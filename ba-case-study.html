01 / ภาพรวมโครงการ

ทำความเข้าใจระบบ
ก่อนกำหนดความต้องการ

วัตถุประสงค์ของโครงการ

ศึกษาการสร้างต้นแบบระบบจดจำใบหน้าแบบเรียลไทม์เพื่อช่วยระบุตัวบุคคล ระบบตรวจจับใบหน้า แปลงใบหน้าเป็นเวกเตอร์คุณลักษณะ เปรียบเทียบกับข้อมูลที่ลงทะเบียนไว้ และเปิดให้ผู้ดูแลตรวจสอบใบหน้าที่ไม่พบข้อมูลตรงกันก่อนพิจารณาเพิ่มข้อมูล

ผู้มีส่วนเกี่ยวข้อง

  • ผู้ดูแลระบบ: ตรวจสอบและจัดการข้อมูลใบหน้า
  • ผู้ใช้งานระบบ: ใช้งานขั้นตอนการจดจำใบหน้า
  • ทีมพัฒนา: พัฒนาและทดสอบการทำงานของระบบ

บทบาทเหล่านี้อนุมานจากต้นแบบ และต้องตรวจสอบยืนยันหากนำระบบไปใช้งานจริง

ประเด็นปัญหาที่ต้องรองรับ

  • เปรียบเทียบใบหน้าที่ตรวจพบกับข้อมูลที่ลงทะเบียนไว้
  • มีขั้นตอนตรวจสอบใบหน้าที่ไม่พบข้อมูลตรงกัน
  • แสดงผลการจดจำให้ผู้ดูแลเข้าใจได้

ภาพรวมเทคโนโลยี

  • Frontend: Next.js
  • Backend: Python + Flask
  • Database: SQLite
  • Face detection: YOLO + NMS
  • Face extracting: InsightFace
  • Searching and compare : KD-Tree and Cosine Similarity

02 / ข้อกำหนด

จากความต้องการทางธุรกิจ
สู่การทำงานของระบบ

ข้อกำหนดทางธุรกิจ (BR) อธิบายผลลัพธ์ที่ระบบควรสนับสนุน ส่วนข้อกำหนดเชิงหน้าที่ (FR) อธิบายพฤติกรรมที่ระบบต้องทำได้ เพื่อนำไปพูดคุย พัฒนา และทดสอบต่อ

📝 ข้อกำหนดทางธุรกิจ (Business Requirements: BR)

  • BR-001: ระบบควรรองรับการระบุตัวบุคคล โดยเปรียบเทียบใบหน้าที่ตรวจพบกับข้อมูลใบหน้าที่ลงทะเบียนไว้
  • BR-002: ผู้ดูแลระบบควรตรวจสอบใบหน้าที่ไม่รู้จัก และเลือกอนุมัติหรือปฏิเสธการเพิ่มข้อมูลใบหน้านั้นได้
  • BR-003: ระบบควรรองรับการจัดเก็บและจัดการข้อมูลใบหน้าที่ลงทะเบียนไว้อย่างเป็นระบบ
  • BR-004 · ข้อเสนอเพิ่มเติม: ก่อนนำไปใช้งานจริง ควรพิจารณาความเป็นส่วนตัว การควบคุมสิทธิ์ การตรวจสอบโดยมนุษย์ และการจัดการกรณีระบบจดจำผิดพลาด

หมายเหตุ: BR-001 ถึง BR-003 อ้างอิงจากขอบเขตของต้นแบบเชิงวิชาการ ส่วน BR-004 เป็นข้อเสนอที่ต้องตรวจสอบกับผู้มีส่วนเกี่ยวข้องเพิ่มเติม

⚙️ ข้อกำหนดเชิงหน้าที่ (Functional Requirements: FR)

  • FR-001: ระบบสามารถรับภาพใบหน้าจากกล้องเว็บแคมได้
  • FR-002: ระบบสามารถตรวจจับตำแหน่งใบหน้าในภาพที่ได้รับได้
  • FR-003: ระบบสามารถแปลงคุณลักษณะใบหน้าเป็นข้อมูลเวกเตอร์ได้
  • FR-004: ระบบสามารถเปรียบเทียบเวกเตอร์กับข้อมูลใบหน้าที่ลงทะเบียนไว้ได้
  • FR-005: ระบบสามารถแสดงผลการจดจำใบหน้าได้
  • FR-006: ระบบสามารถแจ้งหรือแสดงใบหน้าที่ไม่พบข้อมูลตรงกันเพื่อรอการตรวจสอบได้
  • FR-007: ผู้ดูแลระบบสามารถอนุมัติหรือปฏิเสธการเพิ่มข้อมูลใบหน้าใหม่ได้

เกณฑ์การยอมรับ (Acceptance Criteria) ตัวอย่างสำหรับ FR-007

  • เมื่อ มีใบหน้าที่ไม่รู้จักรอการตรวจสอบ และเมื่อ ผู้ดูแลระบบอนุมัติ ผลที่คาดหวังคือ ระบบบันทึกข้อมูลตามขั้นตอนที่กำหนดและแสดงผลการดำเนินการที่ถูกต้อง
  • เมื่อ มีใบหน้าที่ไม่รู้จักรอการตรวจสอบ และเมื่อ ผู้ดูแลระบบปฏิเสธ ผลที่คาดหวังคือ ระบบต้องไม่เพิ่มใบหน้านั้นลงในชุดข้อมูลใบหน้าที่ลงทะเบียนไว้
  • เมื่อ การบันทึกข้อมูลล้มเหลวระหว่างการอนุมัติ ผลที่คาดหวังคือ ระบบแสดงข้อความผิดพลาดและต้องไม่แสดงว่าบันทึกสำเร็จ

เกณฑ์เหล่านี้เป็นข้อเสนอสำหรับกรณีศึกษา ควรตรวจสอบพฤติกรรมจริงของต้นแบบก่อนระบุว่าเป็นความสามารถที่พัฒนาเสร็จแล้ว

03 / USER FLOW

ลำดับการใช้งาน
ตั้งแต่เปิดกล้องจนเห็นคะแนน

แผนภาพนี้แปลงขั้นตอนจาก Flow ต้นฉบับให้เห็นเส้นทางการใช้งานของผู้ใช้ควบคู่กับสิ่งที่ระบบทำเบื้องหลัง โดยคงเทคโนโลยีและลำดับการประมวลผลตามภาพที่ได้รับ

User Flow: การตรวจจับบุคคลและแสดง Familiar Score

ลำดับหลักอ้างอิงจากภาพต้นฉบับ ส่วนกรณีไม่พบคนในวิดีโอแสดงเป็นเส้นทางวนกลับเพื่อรอรับภาพถัดไป

เริ่มต้น
ผู้ใช้เปิดกล้องหรือเริ่มส่งวิดีโอ
ระบบรับวิดีโอแบบเรียลไทม์
YOLO ตรวจจับบุคคลในวิดีโอ
ตรวจพบบุคคลในวิดีโอหรือไม่?

กรณีที่ 1 · ยังไม่พบบุคคล

รอรับภาพหรือเฟรมถัดไปจากกล้อง

เป็นเส้นทางวนกลับที่อนุมานเพื่อให้การรับวิดีโอต่อเนื่อง ไม่ได้แสดงเป็นขั้นตอนแยกในภาพต้นฉบับ

กรณีที่ 2 · พบบุคคล

ประมวลผลกรอบบุคคลด้วย Bounding Box และ IoU
ใช้ DeepFace สกัด Face Embedding
ค้นหาใบหน้าที่คล้ายกันด้วย KD-Tree
ใช้ Cosine Similarity เปรียบเทียบใบหน้า
ใช้ Hierarchical Clustering เพื่อหากลุ่มใบหน้าที่คล้ายกัน
อัปเดต KD-Tree / Familiar Score
ส่ง Familiar Score ผ่าน API
ผู้ใช้เห็น Familiar Score บนเว็บไซต์
จบขั้นตอนการแสดงผล

เส้นทางหลัก (Main Flow)

  1. ผู้ใช้เปิดกล้องหรือเริ่มส่งวิดีโอเข้าสู่ระบบ
  2. YOLO ตรวจจับบุคคลในวิดีโอ และระบบประมวลผล Bounding Box ด้วย IoU
  3. DeepFace สกัด Face Embedding จากใบหน้า
  4. ระบบค้นหาใบหน้าที่คล้ายกันใน KD-Tree และเปรียบเทียบด้วย Cosine Similarity
  5. ระบบใช้ Hierarchical Clustering เพื่อค้นหากลุ่มใบหน้าที่คล้ายกัน และอัปเดต Familiar Score
  6. ระบบส่งคะแนนผ่าน API และแสดง Familiar Score บนเว็บไซต์

เส้นทางทางเลือกและประเด็นที่ต้องยืนยัน

  • ไม่พบบุคคล: แผนภาพเสนอให้ระบบรอรับเฟรมถัดไปเพื่อทำงานต่อเนื่อง โดยควรตรวจสอบกับพฤติกรรมจริงของต้นแบบ
  • ไม่สามารถส่งคะแนนผ่าน API: ภาพต้นฉบับไม่ได้ระบุพฤติกรรมเมื่อเกิดข้อผิดพลาด จึงควรกำหนดและทดสอบเพิ่มเติม
  • การอัปเดตคะแนน: ควรยืนยันวิธีคำนวณ Familiar Score และจังหวะที่ระบบอัปเดตคะแนนกับทีมพัฒนา

04 / การออกแบบการทดสอบ

ข้อกำหนดต้อง ทดสอบได้

รายการต่อไปนี้เป็นกรณีทดสอบที่ออกแบบไว้ ไม่ใช่ผลการทดสอบที่ดำเนินการแล้ว จึงยังไม่ระบุผลผ่านหรือไม่ผ่านจนกว่าจะนำไปทดสอบกับระบบจริง

รหัสทดสอบ ข้อกำหนด สถานการณ์ทดสอบ ผลลัพธ์ที่คาดหวัง สถานะ
TC-001 FR-007 อนุมัติใบหน้าที่ไม่รู้จัก ระบบบันทึกข้อมูลและแสดงผลสำเร็จ ยังไม่ได้ทดสอบ
TC-002 FR-007 ปฏิเสธใบหน้าที่ไม่รู้จัก ระบบไม่เพิ่มใบหน้านั้นลงในข้อมูลที่ลงทะเบียนไว้ ยังไม่ได้ทดสอบ
TC-003 FR-006 ตรวจพบใบหน้าที่ไม่มีข้อมูลตรงกัน ระบบแจ้งหรือแสดงรายการให้ผู้ดูแลตรวจสอบ ยังไม่ได้ทดสอบ
TC-004 FR-007 การบันทึกข้อมูลล้มเหลว ระบบแสดงข้อผิดพลาดและไม่แสดงผลสำเร็จที่ไม่เป็นจริง ยังไม่ได้ทดสอบ
TC-005 FR-004 เปรียบเทียบใบหน้าที่มีข้อมูลลงทะเบียนแล้ว ระบบเปรียบเทียบกับข้อมูลที่ลงทะเบียนและแสดงผลตามที่ตรวจพบ ยังไม่ได้ทดสอบ
TC-006 FR-007 อนุมัติรายการตรวจสอบเดิมซ้ำ ข้อเสนอ: ระบบควรป้องกันการลงทะเบียนข้อมูลซ้ำ ยังไม่ได้ทดสอบ

ขอบเขตที่ครอบคลุม

กรณีทดสอบที่ออกแบบไว้เน้นขั้นตอนการตรวจสอบใบหน้าใหม่และการตัดสินใจของผู้ดูแล นอกจากนี้ควรทดสอบการตรวจจับและการเปรียบเทียบใบหน้าในกรณีใบหน้าที่รู้จักและไม่รู้จัก แสงแตกต่างกัน มุมใบหน้าแตกต่างกัน และรูปลักษณ์เปลี่ยนไป

ประเด็นที่ยังต้องกำหนด

เกณฑ์ความแม่นยำ เป้าหมายด้านประสิทธิภาพ ระยะเวลาจัดเก็บข้อมูลส่วนบุคคล และสิทธิ์การเข้าถึง ต้องได้รับการยืนยันจากผู้มีส่วนเกี่ยวข้อง ไม่ควรกำหนดตัวเลขขึ้นเองหากไม่มีผลทดสอบหรือข้อกำหนดที่ตกลงกันไว้

05 / เอกสารประกอบ

เอกสารที่ใช้ประกอบ กรณีศึกษา

สามารถเปิดเอกสารต้นฉบับเพื่ออ่านรายละเอียดเพิ่มเติม เอกสารเหล่านี้เป็นร่างสำหรับ Portfolio และสามารถปรับปรุงได้เมื่อมีการตรวจสอบข้อมูลของโครงการเพิ่มเติม

ข้อกำหนดการทำงานและเกณฑ์การยอมรับ 03 · เอกสาร Use Case

สถานการณ์ทดสอบและผลลัพธ์ที่คาดหวัง 05 · ตารางเชื่อมโยงข้อกำหนด (RTM)
